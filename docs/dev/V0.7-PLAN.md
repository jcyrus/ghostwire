# ZeroDrop v0.7.0 Implementation Plan

## Executive Summary

v0.7.0 upgrades ZeroDrop's cryptographic layer from a symmetric-only per-message ratchet to a full Signal-style DH Double Ratchet for pairwise DMs, providing post-compromise security (self-healing after key exposure). Group encryption gains a sender-ratchet announcement mechanism that triggers key redistribution when a sender's ratchet public key rotates. On the server side, per-IP rate limiting via `tower_governor` mitigates connection floods and AUTH spam, and relay-level delivery receipts give senders a lightweight in-flight ACK when a DM is successfully delivered to the recipient's WebSocket buffer. All four features are additive and backward-compatible with v0.6 clients.

---

## Feature 1: DH Double Ratchet for DMs

### What Changes

**`client/src/crypto.rs`**
- Add `kdf_rk(root_key: &[u8;32], dh_output: &[u8;32]) -> ([u8;32], [u8;32])` — the root-key KDF applied on every DH ratchet step.

**`client/src/keystore.rs`**
- Add four fields to `PeerSession`: `root_key: [u8;32]`, `ratchet_secret: StaticSecret`, `ratchet_public: PublicKey`, `their_ratchet_public: PublicKey`.
- Add `pending_ratchet_keys: HashMap<String, PublicKey>` to `KeyStore` to hold each peer's init ratchet public key between KEY_EXCHANGE parse and `establish_session`.
- Add `store_peer_ratchet_key_decoded(&mut self, username: &str, key: PublicKey)` and `take_peer_ratchet_key(&mut self, username: &str) -> Option<PublicKey>` to `KeyStore`.
- Modify `establish_session` to read from `pending_ratchet_keys` and apply the DH-init step when the peer's init ratchet key is present.
- Add `perform_recv_dh_ratchet(&mut self, their_new_ratchet: PublicKey)` on `PeerSession` — executes the double-ratchet receive logic.
- Clear `pending_ratchet_keys` in `clear_all_sessions`.

**`client/src/app.rs`**
- Add `#[serde(default)] #[serde(skip_serializing_if = "Option::is_none")] pub ratchet_key: Option<String>` to `WireMessage`.
- Add `#[serde(other)] Unknown` catch-all variant to `MessageType` (enables silent discard of unrecognized message types including v0.8+ additions).

**`client/src/network.rs`**
- `build_key_exchange_message`: add `ratchet_key_b64: Option<String>` parameter; populate it from the local keystore's init ratchet public key.
- KEY_EXCHANGE receive handler: decode `wire_msg.ratchet_key` and call `store_peer_ratchet_key_decoded` before `establish_session`.
- DM send handler: include `ratchet_key: Some(encode_public_key(&session.ratchet_public))` on all outgoing encrypted DMs.
- DM receive handler (`handle_wire_message`, `MessageType::Message`): before `derive_recv_key`, check `wire_msg.ratchet_key`; if present and different from `session.their_ratchet_public`, call `session.perform_recv_dh_ratchet`. If absent, skip the DH step (v0.6 fallback).
- Add `_ => {}` arm to the `handle_wire_message` match for `MessageType::Unknown`.

### Protocol / Wire Format

**KEY_EXCHANGE message** (JSON, broadcast then targeted):
```json
{
  "type": "KEY_EXCHANGE",
  "payload": "<base64 X25519 ephemeral public key>",
  "ratchet_key": "<base64 X25519 init ratchet public key>",
  "channel": "global",
  "meta": { "sender": "alice", "timestamp": 1748000000 }
}
```

`ratchet_key` is absent on v0.6 clients. If a received KEY_EXCHANGE has no `ratchet_key`, `establish_session` falls back to the v0.6 symmetric-only path (chains derived directly from `chain_key` using lex-ordering labels). No old client breaks.

**DM message** (JSON, unicast or broadcast fallback):
```json
{
  "type": "MSG",
  "payload": "<base64 ChaCha20-Poly1305 ciphertext>",
  "ratchet_key": "<base64 current ratchet public key>",
  "channel": "dm:alice:bob",
  "encrypted": true,
  "recipient": "bob",
  "meta": { "sender": "alice", "timestamp": 1748000000 },
  "message_id": "<uuid>"
}
```

`ratchet_key` is absent on plaintext and non-DM messages. Old clients receiving a DM with a `ratchet_key` ignore it (unknown JSON field, `serde` default). When an old client sends a DM without `ratchet_key`, the receiver falls through to symmetric-only decrypt.

### Implementation Steps

**1. Add `kdf_rk` to `crypto.rs`.**

```rust
pub fn kdf_rk(root_key: &[u8; 32], dh_output: &[u8; 32]) -> ([u8; 32], [u8; 32]) {
    let hkdf = Hkdf::<Sha256>::new(Some(root_key), dh_output);
    let mut new_root  = [0u8; 32];
    let mut new_chain = [0u8; 32];
    hkdf.expand(b"ZeroDrop-DH-Ratchet-v0.7-root",  &mut new_root).expect("HKDF expand");
    hkdf.expand(b"ZeroDrop-DH-Ratchet-v0.7-chain", &mut new_chain).expect("HKDF expand");
    (new_root, new_chain)
}
```

Pure function; no side effects. Add two unit tests: `test_kdf_rk_deterministic` (same inputs → same outputs) and `test_kdf_rk_distinct_inputs_produce_distinct_chains`.

**2. Add ratchet fields to `PeerSession` in `keystore.rs`.**

```rust
pub struct PeerSession {
    // ... existing fields ...
    pub root_key:             [u8; 32],
    pub ratchet_secret:       StaticSecret,
    pub ratchet_public:       PublicKey,
    pub their_ratchet_public: PublicKey,
}
```

`StaticSecret` from `x25519-dalek` already implements `ZeroizeOnDrop` when the `"zeroize"` feature is active (it is, per `Cargo.toml`). Add `root_key` to the existing manual `Drop`/`Zeroize` path for `PeerSession` (currently the struct uses per-field zeroize; `root_key` is `[u8;32]` which implements `Zeroize`). `PeerSession` is not `Clone`-derived; the `!Clone` bound on `StaticSecret` enforces this at compile time.

**3. Add `pending_ratchet_keys` to `KeyStore` and its accessors.**

```rust
pending_ratchet_keys: HashMap<String, PublicKey>,
```

In `KeyStore::new()`: `pending_ratchet_keys: HashMap::new()`.
In `clear_all_sessions()`: add `self.pending_ratchet_keys.clear()`.

New methods:
```rust
pub fn store_peer_ratchet_key_decoded(&mut self, username: &str, key: PublicKey) {
    self.pending_ratchet_keys.insert(username.to_string(), key);
}

fn take_peer_ratchet_key(&mut self, username: &str) -> Option<PublicKey> {
    self.pending_ratchet_keys.remove(username)
}
```

Also add `get_our_ratchet_init_public_key() -> String` that returns `encode_public_key(&self.ratchet_init_keypair.public)` — see step 4 for where `ratchet_init_keypair` lives.

**4. Add `ratchet_init_keypair` to `KeyStore` and update `establish_session`.**

Add field `ratchet_init_keypair: EphemeralKeypair` to `KeyStore`, generated in `new()` and regenerated in `rotate_ephemeral_key()` (alongside the existing ephemeral key regeneration).

Extend `establish_session` — after the existing chain derivation, check for a pending init ratchet key:

```rust
if let Some(their_init_ratchet) = self.take_peer_ratchet_key(username) {
    // ── DH-init step ──────────────────────────────────────────────────
    // Use our init ratchet keypair (the one advertised in KEY_EXCHANGE)
    // for the bootstrap DH. Both sides compute the same dh_init because
    // ECDH is commutative: ECDH(a_secret, B_pub) = ECDH(b_secret, A_pub).
    let dh_init = self.ratchet_init_keypair.secret.diffie_hellman(&their_init_ratchet);
    let (root1, init_chain) = kdf_rk(&session_keys.chain_key, dh_init.as_bytes());

    // Derive role-differentiated send/recv chains from init_chain
    // using the same lex-ordering label logic as before.
    let our_init_pub   = self.ratchet_init_keypair.public.as_bytes();
    let their_init_pub = their_init_ratchet.as_bytes();
    let (send_label, recv_label): (&[u8], &[u8]) = if our_init_pub < their_init_pub {
        (b"send", b"recv")
    } else {
        (b"recv", b"send")
    };
    let hkdf = Hkdf::<Sha256>::new(None, &init_chain);
    hkdf.expand(send_label, &mut send_chain).expect("HKDF");
    hkdf.expand(recv_label, &mut recv_chain).expect("HKDF");

    // ── Generate ongoing ratchet keypair ──────────────────────────────
    // Not the init keypair (already shared in KEY_EXCHANGE) — a fresh one.
    let ongoing_ratchet = generate_ephemeral_keypair();
    let dh2 = ongoing_ratchet.secret.diffie_hellman(&their_init_ratchet);
    let (root2, new_send_chain) = kdf_rk(&root1, dh2.as_bytes());
    send_chain = new_send_chain;

    session = PeerSession {
        // ... existing fields ...
        root_key:             root2,
        ratchet_secret:       ongoing_ratchet.secret,
        ratchet_public:       ongoing_ratchet.public,
        their_ratchet_public: their_init_ratchet,
        send_chain, recv_chain,
        // ... rest ...
    };
} else {
    // v0.6 fallback: no DH step, root_key = chain_key, generate a
    // ratchet keypair anyway so outbound DMs always carry a valid key.
    let fallback_ratchet = generate_ephemeral_keypair();
    session = PeerSession {
        root_key:             session_keys.chain_key,
        ratchet_secret:       fallback_ratchet.secret,
        ratchet_public:       fallback_ratchet.public,
        their_ratchet_public: their_public_key, // use the ephemeral as placeholder
        // ... existing fields ...
    };
}
```

**5. Add `perform_recv_dh_ratchet` to `PeerSession` in `keystore.rs`.**

```rust
/// Execute a DH ratchet step on receiving a message with a new peer ratchet key.
/// Called before the symmetric recv-chain advance when `their_new_ratchet ≠ their_ratchet_public`.
pub fn perform_recv_dh_ratchet(&mut self, their_new_ratchet: PublicKey) {
    // Step 1: derive new recv chain from current ratchet secret + new peer key.
    let dh = self.ratchet_secret.diffie_hellman(&their_new_ratchet);
    let (root1, recv_chain) = kdf_rk(&self.root_key, dh.as_bytes());

    // Step 2: generate fresh ratchet keypair; derive new send chain.
    let new_kp = generate_ephemeral_keypair();
    let dh2 = new_kp.secret.diffie_hellman(&their_new_ratchet);
    let (root2, send_chain) = kdf_rk(&root1, dh2.as_bytes());

    // Commit all state atomically.
    self.root_key             = root2;
    self.recv_chain           = recv_chain;
    self.recv_counter         = 0;
    self.send_chain           = send_chain;
    self.send_counter         = 0;
    self.their_ratchet_public = their_new_ratchet;
    self.ratchet_secret       = new_kp.secret;
    self.ratchet_public       = new_kp.public;
}
```

The method is `&mut self` on `PeerSession` to keep the logic adjacent to the session state and avoid re-borrowing `KeyStore` mid-call.

**6. Update `WireMessage` in `app.rs`.**

Add to the `WireMessage` struct:
```rust
#[serde(default)]
#[serde(skip_serializing_if = "Option::is_none")]
pub ratchet_key: Option<String>,
```

Add to `MessageType`:
```rust
#[serde(other)]

```

Run `grep -n "WireMessage {" client/src/network.rs` to enumerate every literal — there are roughly 12. Add `ratchet_key: None` to each (or the appropriate `Some(...)` for KEY_EXCHANGE and DM sends). The compiler will reject any that are missed (exhaustive struct initialization).

**7. Update `build_key_exchange_message` in `network.rs`.**

Add parameter `ratchet_key_b64: Option<String>`. Two call sites: initial connect and targeted re-exchange on peer AUTH. Both call `keystore.get_our_ratchet_init_public_key()` to populate the parameter.

**8. Update KEY_EXCHANGE receive handler in `handle_wire_message`.**

After decoding `their_pk` from `msg.payload`:
```rust
if let Some(rk_b64) = &msg.ratchet_key {
    if let Ok(rk) = decode_public_key(rk_b64) {
        store.store_peer_ratchet_key_decoded(&their_username, rk);
    }
}
```
Then call `store.establish_session(&their_username)` as before.

**9. Update DM send path in `network.rs`.**

After locking the keystore and confirming a session exists, read `ratchet_public` before calling `derive_send_key` (avoids a double lock). Set `ratchet_key: Some(encode_public_key(&ratchet_pub))` on the outgoing `WireMessage` for all encrypted DMs. For unencrypted messages (global channel), keep `ratchet_key: None`.

**10. Update DM receive path in `handle_wire_message`.**

Insert before the existing `derive_recv_key` call:
```rust
if let Some(rk_b64) = &msg.ratchet_key {
    if let Ok(their_new_rk) = decode_public_key(rk_b64) {
        if their_new_rk.as_bytes() != session.their_ratchet_public.as_bytes() {
            session.perform_recv_dh_ratchet(their_new_rk);
        }
    }
}
```

**11. Handle ratchet state across key rotation.**

`rotate_ephemeral_key()` regenerates `self.ephemeral`. At the same point, regenerate `self.ratchet_init_keypair`. After rotation the re-broadcast KEY_EXCHANGE carries the new init ratchet public key. `pending_ratchet_keys` is cleared in `clear_all_sessions()` (called from `rotate_ephemeral_key`) so stale init ratchet keys from the previous epoch are discarded.

## Feature 2: Group Sender-Key Ratchet per Message

### What Changes

**`client/src/keystore.rs`**
- Add `ratchet_public: PublicKey` and `ratchet_secret: StaticSecret` to `SenderKeyState`. Generate in `SenderKeyState::generate()`. Populate `ratchet_public` (but set `ratchet_secret` to a zero sentinel) in `from_distribution`.
- Extend `store_sender_key` signature: add `ratchet_public: PublicKey` parameter. Update the de-dup guard to also check `ratchet_public` byte equality. Update `from_distribution` to accept `ratchet_public`.
- Add `KeyStore::get_group_send_ratchet_public(group_id: &str) -> Option<PublicKey>` accessor.

**`client/src/network.rs`**
- `DistributeGroupKey` handler: extend distribution payload from 64 to 96 bytes (`key || chain_key || ratchet_public`). Update decode path: `payload_bytes.len() == 96` for new clients, `== 64` accepted as v0.6 fallback with zero-sentinel ratchet public.
- Group message send: include `ratchet_key: Some(encode_public_key(&ratchet_pub))` on outgoing group `WireMessage`.
- Group message receive: after decryption, compare `msg.ratchet_key` to stored `SenderKeyState.ratchet_public` for the sender. If they differ, remove the stale state and emit `NetworkEvent::GroupSenderKeyRotated { group_id, sender }`.
- Add `NetworkEvent::GroupSenderKeyRotated { group_id: String, sender: String }`.

**`client/src/main.rs`**
- Handle `NetworkEvent::GroupSenderKeyRotated`: display a system message `"[group_id] {sender}'s sender key rotated — they need to re-run /groupkey"`.

### Protocol / Wire Format

**SENDER_KEY distribution payload** (96 bytes, base64-encoded, inside an encrypted DM):
```
bytes  0..32 = sender symmetric key
bytes 32..64 = sender chain_key
bytes 64..96 = sender ratchet_public (X25519, 32 bytes)
```

Old clients distributing 64-byte payloads: new receivers treat `ratchet_public` as `[0u8;32]` (sentinel); rotation comparison is skipped for this sender. New clients distributing 96-byte payloads: old receivers fail the `len == 64` check and reject the distribution — this is the intended migration cutover. Document in release notes.

**Group message**: `ratchet_key` field set to sender's current ratchet public (same field as DM). Old clients ignore it.

### Implementation Steps

1. Extend `SenderKeyState` struct. In `generate()`, call `generate_ephemeral_keypair()` for ratchet fields. In `from_distribution(key, chain_key, ratchet_public)`, set `ratchet_public` and `ratchet_secret = StaticSecret::from([0u8;32])`.

2. Update `store_sender_key` signature and body: add `ratchet_public: PublicKey`, update the de-dup check, pass to `from_distribution`.

3. Add `get_group_send_ratchet_public` to `KeyStore`.

4. Extend `DistributeGroupKey` handler: read ratchet public via new accessor, build 96-byte payload, send. Update the receiver's decode path to handle both 64- and 96-byte payloads.

5. Update group message send in `network.rs`: populate `ratchet_key` from the sender's `SenderKeyState.ratchet_public`.

6. Update group message receive: after decryption, check `ratchet_key` vs stored value. On mismatch, remove stale state and emit `GroupSenderKeyRotated`.

7. Handle `GroupSenderKeyRotated` in `main.rs`: find the group channel by `group_id`, append a system message.

8. Group sender ratchet key rotation happens automatically when `/groupkey` regenerates `SenderKeyState` via `SenderKeyState::generate()` (which already regenerates all fields). No structural change needed — only the payload size change ensures peers notice the new ratchet public.

### Test Plan

- `test_sender_key_state_generate_has_ratchet_public`: Non-zero `ratchet_public` after `generate()`.
- `test_store_sender_key_96_byte_payload`: Build 96-byte payload, call `store_sender_key`, assert stored ratchet public matches.
- `test_store_sender_key_64_byte_fallback`: 64-byte payload accepted; zero-sentinel ratchet public stored.
- `test_group_sender_key_rotation_detected`: Store sender key with ratchet pub A. Call the receive path with `ratchet_key` = pub B. Assert `GroupSenderKeyRotated` is emitted and the stale state is removed.
- `test_group_sender_key_unchanged_no_rotation`: Same ratchet key as stored. Assert no rotation event.

## Feature 3: Per-IP Rate Limiting (Server)

### What Changes

**`server/Cargo.toml`**
- Add `tower_governor = "0.8"`. Note: `"0.4"` was the original plan but caused an `axum-core` version conflict (`Body` type mismatch against axum 0.8 / axum-core 0.5); `"0.8"` resolves this.

**`server/src/util.rs`** (new shared module)
- `pub fn real_ip(headers: &HeaderMap, peer_addr: Option<SocketAddr>) -> IpAddr` — checks `Fly-Client-IP`, then `X-Forwarded-For` (first token), then `peer_addr`, then `127.0.0.1`.

**`server/src/relay.rs`**
- Add `auth_rate: Arc<Mutex<HashMap<IpAddr, (u32, Instant)>>>` to `RelayState`.
- Add `pub fn check_and_record_auth(&self, ip: IpAddr) -> bool` — 60 AUTH messages per IP per 60-second sliding window.
- Update `relay` method signature to `async fn relay(&self, from: ClientId, from_ip: IpAddr, content: String)`. Pass `from_ip` through to `check_and_record_auth` when `env.msg_type == "AUTH"`.
- Store `from_ip: IpAddr` in `ClientHandle` for pruning auth rate entries on disconnect.
- Update `unregister_client` to prune `auth_rate` on client disconnect.

**`server/src/main.rs`** and **`server/src/local.rs`**
- Add `mod util;` and use `util::real_ip`.
- Apply `GovernorLayer` (connection-level rate limit: 10 connections per IP per minute, burst 3) to the `/ws` route using a custom `KeyExtractor` wrapping `real_ip`.
- Extract real IP before WebSocket upgrade and pass to `handle_websocket`.
- Update `into_make_service_with_connect_info::<SocketAddr>()` in `local.rs` so `ConnectInfo<SocketAddr>` is available for the fallback IP path.

### Protocol / Wire Format

No wire changes. Rate limiting is transparent to clients. Connection-rate-exceeded → HTTP 429 at the upgrade layer (before WebSocket is established). AUTH-flood-exceeded → AUTH messages silently dropped for the current 60-second window; connection remains open.

### Implementation Steps

1. Add `tower_governor` to `server/Cargo.toml`. Pin exact minor version; add explanatory comment.

2. Create `server/src/util.rs`:
   ```rust
   pub fn real_ip(headers: &HeaderMap, peer_addr: Option<SocketAddr>) -> IpAddr {
       if let Some(v) = headers.get("Fly-Client-IP")
           .and_then(|v| v.to_str().ok())
           .and_then(|s| s.parse::<IpAddr>().ok()) { return v; }
       if let Some(v) = headers.get("X-Forwarded-For")
           .and_then(|v| v.to_str().ok())
           .and_then(|s| s.split(',').next())
           .and_then(|s| s.trim().parse::<IpAddr>().ok()) { return v; }
       peer_addr.map(|a| a.ip()).unwrap_or(IpAddr::V4(Ipv4Addr::LOCALHOST))
   }
   ```

3. Add `auth_rate` field to `RelayState` and its `new()`/`with_limits()` constructors. Add `check_and_record_auth`. Store `from_ip` in `ClientHandle`. Prune `auth_rate` in `unregister_client`.

4. Update `relay` and `handle_websocket` to thread `from_ip: IpAddr` through.

5. Implement `RealIpExtractor` for `tower_governor`'s `KeyExtractor` trait. Apply `GovernorLayer` to `/ws` route in both `main.rs` and `local.rs`. For Shuttle (`main.rs`), rely on header-only IP extraction (Fly always provides `Fly-Client-IP`). For `local.rs`, use `into_make_service_with_connect_info::<SocketAddr>()`.

6. Add `mod util;` to both `main.rs` and `local.rs`.

- `test_real_ip_fly_header`: `Fly-Client-IP: 1.2.3.4` → returns `1.2.3.4`.
- `test_real_ip_xforwardedfor_first_hop`: `X-Forwarded-For: 10.0.0.1, 10.0.0.2` → returns `10.0.0.1`.
- `test_real_ip_peer_addr_fallback`: Empty headers, peer addr `127.0.0.1:9999` → returns `127.0.0.1`.

## Feature 4: Relay-Level Delivery Receipts

### What Changes

- Add private method `send_ack(&self, sender_id: ClientId, message_id: String, recipient: String)` — unicasts an ACK JSON frame back to the sender after a successful DM unicast.
- In `relay`, call `send_ack` after a successful `unicast` when `env.meta.message_id.is_some()`.

**`client/src/app.rs`**
- Add `#[serde(rename = "ACK")] Ack` to `MessageType`.
- Add `pub enum DeliveryStatus { Sent, Delivered }` to `app.rs`.
- Add `pub delivery_status: DeliveryStatus` to `ChatMessage`; default `Sent` in all constructors.

**`client/src/network.rs`**
- Add `NetworkEvent::MessageDelivered { message_id: String, recipient: String }`.
- Handle `MessageType::Ack` in `handle_wire_message`: emit `NetworkEvent::MessageDelivered`.

**`client/src/main.rs`**
- Handle `NetworkEvent::MessageDelivered`: look up the DM channel, find `ChatMessage` by `id`, set `delivery_status = Delivered`.

**`client/src/ui.rs`**
- Add `delivery_indicator_span(status: &DeliveryStatus) -> Span<'static>`: `✓` (dark gray) for `Sent`, `✓✓` (cyan) for `Delivered`.
- Append indicator to the last line of own messages in `render_messages`. System messages and action messages are excluded.

### Protocol / Wire Format

**ACK frame** (relay → sender only, JSON):
```json
{
  "type": "ACK",
  "payload": "",
  "channel": "global",
  "meta": { "sender": "_relay", "timestamp": 1748000001 },
  "message_id": "<uuid from original message>",
  "recipient": "bob",
  "encrypted": false
}
```

The relay generates this frame in `send_ack` using `serde_json::json!` — not a raw format string — to safely interpolate `message_id` (which comes from the client's own wire message; a malicious client could inject arbitrary JSON if not serialized properly).

Old clients receive an ACK with `"type":"ACK"`. If `MessageType::Unknown` is not added (Feature 1 adds it), the `serde` enum deserialization will fail and the WebSocket receive loop will log a parse error and drop the frame. To prevent this noise, add `MessageType::Unknown` (step added in Feature 1) before merging Feature 4. The sequencing section below accounts for this.

**EnvelopeMeta extension** (relay, `relay.rs`):
```rust
#[derive(Debug, Default, Deserialize)]
struct EnvelopeMeta {
    #[serde(default)] sender:     String,
    #[serde(default)] message_id: Option<String>,
}
```

### Implementation Steps

1. Add `message_id: Option<String>` to `EnvelopeMeta` in `relay.rs`.

2. Add `send_ack` to `RelayState`:
   ```rust
   async fn send_ack(&self, sender_id: ClientId, message_id: String, recipient: String) {
       use serde_json::json;
       let ts = std::time::SystemTime::now()
           .duration_since(std::time::UNIX_EPOCH)
           .map(|d| d.as_millis() as i64)
           .unwrap_or(0);
       let ack = json!({
           "type": "ACK",
           "payload": "",
           "channel": "global",
           "meta": { "sender": "_relay", "timestamp": ts },
           "message_id": message_id,
           "recipient": recipient,
           "encrypted": false
       }).to_string();
       self.unicast(sender_id, ack).await;
   }
   ```

3. In `relay`, after `self.unicast(target, content).await`, add:
   ```rust
   if let Some(mid) = env.meta.message_id {
       self.send_ack(from, mid, recipient.to_string()).await;
   }
   return;
   ```
   (The `return` is the existing one; move the ACK send before it.)

4. Add `Ack` to `MessageType`, `DeliveryStatus` enum, and `delivery_status` field to `ChatMessage` in `app.rs`. Initialize `delivery_status: DeliveryStatus::Sent` in all constructors.

5. Add `NetworkEvent::MessageDelivered` and handle `MessageType::Ack` in `handle_wire_message`:
   ```rust
   MessageType::Ack => {
       if let Some(mid) = msg.message_id {
           let recip = msg.recipient.unwrap_or_default();
           let _ = event_tx.send(NetworkEvent::MessageDelivered {
               message_id: mid, recipient: recip,
           });
       }
   }
   ```

6. Handle `NetworkEvent::MessageDelivered` in `main.rs`: compute the canonical DM channel (`dm:min:max` by lex sort of the two usernames), iterate its messages with `iter_mut()`, find `m.id == message_id`, set `m.delivery_status = DeliveryStatus::Delivered`. If the channel does not exist, ignore.

7. Add `delivery_indicator_span` to `ui.rs`. In `render_messages`, for non-system, non-action messages where `msg.sender == app.username`, append the indicator span to the last line's `Line` in the rendered output.

8. Update relay tests: extend `dm_is_unicast_only_to_recipient` to add a `message_id` to `dm_json` and assert Alice's rx buffer contains an ACK frame after the relay call.

## Risks and Mitigations

**Risk 1: Ratchet bootstrap race (KEY_EXCHANGE arrives after first DM).**
If a DM arrives before the peer's KEY_EXCHANGE (carrying their init ratchet key), the session falls back to symmetric-only v0.6 behavior. The DH ratchet activates on the next KEY_EXCHANGE round, which the staggered-join re-exchange logic in `network.rs` already triggers. Both sides degrade gracefully to v0.6, which is safe. Covered by `test_no_ratchet_key_falls_back_to_symmetric`.

**Risk 2: `StaticSecret` is `!Clone`.**
`PeerSession` will not be `Clone`-derivable after this change (it already is not). Confirm no code path clones it. Add a doc comment on the struct noting the non-clone constraint to prevent future regressions.

**Risk 3: `kdf_rk` with the same bootstrap DH output gives the same chains on both sides.**
The bootstrap DH `ECDH(our_init_ratchet_secret, their_init_ratchet_public)` produces the same output on both sides (DH commutativity). Both sides derive the same `init_chain`, then split it into `send_chain`/`recv_chain` via lex-ordering labels — this correctly differentiates roles. The test `test_double_ratchet_session_establishment` must assert `alice.send_chain == bob.recv_chain` and `alice.recv_chain == bob.send_chain`.

**Risk 4: `tower_governor` API compatibility.**
Pin the exact minor version. If 0.4.x is incompatible with the project's `tower 0.5` transitive dependency, use `tower_governor 0.3.x` (which targets `tower 0.4`) by also patching `tower` in `[patch.crates-io]`. Document the constraint. The rate-limiting logic itself is in a standalone function (`check_and_record_auth`) that does not depend on `tower_governor`; only the middleware wiring does.

**Risk 5: Shuttle runtime does not expose `ConnectInfo<SocketAddr>`.**
Header-only IP extraction (`Fly-Client-IP`) is the fallback for Shuttle. If neither header is present (local testing without a proxy), rate-limit keys default to `127.0.0.1` — all local test connections share one bucket. This is acceptable in local development. Add a `warn!` log when the fallback fires in production.

**Risk 6: ACK delivery state lost on reconnect.**
ACKs are in-flight only. After a reconnect, unacknowledged messages remain at `Sent` forever. This is documented as an explicit scope limitation of v0.7. Persistent delivery receipts are deferred to v0.8+.

**Risk 7: Group distribution payload size breaks v0.6 clients.**
Old receivers reject 96-byte distributions (`len == 64` check fails). Document the migration in the v0.7 release notes: mixed v0.6/v0.7 groups require all members to upgrade before group messages resume. The `/groupkey` re-distribution command is still available for manual recovery.

**Risk 8: `perform_recv_dh_ratchet` called twice for the same ratchet key.**
The call-site guard `their_new_rk.as_bytes() != session.their_ratchet_public.as_bytes()` prevents re-entry. Covered by the round-trip test: replaying the same `ratchet_key` on a second message must decrypt correctly (the second message uses the already-advanced symmetric chain, not a second DH step).
